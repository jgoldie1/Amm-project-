# GoogleX Quantum Memory — TRYAMM agent skill

## Activation
When an agent receives a request to continue, repair, extend, deploy, integrate or recall TRYAMM work, first read repository-root `README.md`, `AGENTS.md`, and `docs/architecture/GOOGLEX_MEMORY_GITHUB_CONTINUITY_BRIDGE.md`. Then locate **existing code** and current GitHub commits, tests and open PRs. Do not interpret this skill as automatic ChatGPT conversation memory.

## Principle
GoogleX is **connected, versioned, recoverable project knowledge**, not a claim of quantum hardware. Each trustworthy memory record needs:
- stable record ID, project and tenant/workspace scope;
- source URI/path, source revision/commit, captured time and confidence;
- permissions, consent status, revocation and expiry;
- content hash/checkpoint ID and relationship to related assets;
- authoritative state: envisioned, documented, coded, tested, device-verified or deployed.

## Required work sequence
1. Identify the current scope (business, player, world, media, public project metadata) and verify authorization.
2. Retrieve the minimum relevant sources; cite their revisions. Never load secrets, intimate-device telemetry or private identities into public agent context or advertising.
3. Compare requested functionality with existing modules; prefer an adapter or repair over replacing working code.
4. For a bug: collect red test and exact logs, normalize failure signature, isolate minimal patch, run targeted and regression green tests, check mobile accessibility and security, prepare human-reviewed PR.
5. For an asset: validate license, performer consent, version, integrity and mobile budget; connect via Universal Creation Graph to StreetVerse, HoloVerse, CrossVerse, LIVE, Omni Box or authorized business surfaces.
6. For an ad: use a business-authorized Holo Ads **draft**; require independent approval and server-confirmed payments before publication; never target using GoogleX private memory.
7. For a release: preserve source SHA, dependency evidence, screenshots, signed artifact/checksum where relevant, save-state recovery and rollback pointer. Do not deploy automatically.
8. Record a checkpoint: what was changed, what is proven, what failed, remaining blocker and what to do next.
