# Expandable website template catalog

The independent business app includes sixteen built-in industry starter templates. Added categories are cleaning, home repair/trades, real estate/property, fashion, tutoring/classes and fitness/coaching. Each has a description, audience, benefits, scope, price and interactive sample. Search filters by name, audience and suitable business types. The ten-business free-template pilot remains ten gifts, regardless of the number of catalog entries.

The owner studio starts from a built-in template, edits metadata, one-time USD price and up to six demo services/products, and previews the same interaction used in the public gallery. Explicit device saving, JSON download and import preserve local drafts. Imported/device drafts never grant publishing authority and require saved-listing reload before updates. The supported product is a configurable starter layout; arbitrary code upload and automated hosting installation are not supplied.

`/api/templates/catalog` returns only validated published fields. Owner GET/POST/PATCH require verified Supabase authentication and `TRYAMM_TEMPLATE_OWNER_USER_IDS` or trusted app_metadata role template-admin/founder/superadmin/platform-admin. Self-editable user metadata and support-only roles do not grant publishing. Owner identity is server assigned. Every update requires the last saved revision to prevent overwrites. Publishing requires explicit content rights confirmation and current-demo review. Archiving removes a listing from successful subsequent public fetches. Reads are bounded to 200 additional listings.

The managed migration creates `tryamm_website_templates` with RLS and no anonymous/authenticated direct privileges; only the server can read/write. Public API sanitization prevents private draft/owner fields from being exposed. Built-ins remain usable during provider outages.

Checkout remains disabled. The connected Stripe account observed October 19 was test mode, charges_enabled=false, payouts_enabled=false and details_submitted=false. The app payment-status proxy timed out. The configured Supabase project contained zero auth users, so no owner identity could safely be assigned. Before selling: identify the owner's actual account, verify authenticated draft-save/publish/archive through the deployed API, connect an active live Stripe account and server credentials securely, wire price-authoritative checkout to immutable delivered-template revisions and payment webhooks, then test paid/download/refund/retry behavior before enabling charging. Never infer profit from the displayed template price.

Validation includes price/input rejection, trusted-role checks, draft confidentiality, immutable owner assignment, conflict handling, no false save/publication on outages, database privileges, mobile draft download/restore, all sixteen demos and source preservation of the working StreetVerse release.

## Credential and provider repair found during release

The previously public Supabase client credential decoded to the service_role role. No credential value is stored here. The Vercel production browser variable was replaced with the project’s enabled publishable key. A Vite configResolved guard rejects privileged Supabase credentials in browser-visible environment variables and omits values from errors. Tests use synthetic credentials only. The exposed legacy server key still needs coordinated revocation/rotation through Supabase settings and server consumers must receive the replacement privately. This is required even after removing the key from the newest frontend.

An authenticated health/read check returned HTTP 402 with exceed_cached_egress_quota. The provider says the owner must address the plan/spend cap to restore service. No upgrade, spend-cap removal, key revocation or billing change was made by this release. The available connector does not expose credential rotation. Existing sessions and services must be considered when the owner performs that rotation.
